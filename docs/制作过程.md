## 一、需求起源

### 1.1 原始诉求

用户（AI 产品经理求职者）在 BOSS直聘 上投递岗位时，需要针对**每一个不同岗位**发送定制化的打招呼自我介绍，但手写调整耗时且容易遗漏岗位关键词。

用户提供的基础自我介绍模板：

```
您好，我是<你的姓名>，对您这个 AI 岗位方向很感兴趣
擅长把 AI 想法变成真上线的生产系统：To C 医疗导购和 To B Agent 平台都交付过
近6 年互联网经验，2年 AI / Agent 产品经验：<某医疗互联网公司> AI 导购准确率 67%→95%；
<某 To B Agent 公司>优化迭代 To B Agent 平台功能，并行交付 2个 B 端客户AI agent定制化项目
有作品集可发，期待您的回复~
```

### 1.2 核心诉求演进

| 阶段 | 诉求 | 说明 |
|---|---|---|
| 1 | 打开 BOSS 岗位页 → 自动改自我介绍 | 最初的模糊设想 |
| 2 | 能读岗位内容 + 生成定制文案 | 明确功能边界 |
| 3 | 岗位 JD 禁止复制怎么办 | 遇到反爬限制 |
| 4 | 做成 Chrome 扩展，直接读页面 DOM | 绕过复制限制 |
| 5 | 界面要好看，做成猫猫打招呼动态 | 视觉升级 |
| 6 | 用**自己的真实宠物猫** + 电钻主题 | 个性化 |
| 7 | 猫猫可拖动、动画不掉帧 | 体验打磨 |

## 二、方案选型

### 2.1 方案 A：DSH Cordis 动态插件（第一版，已存档）

**设计**：在 DeepSeek Harness 内做一个插件，
- **Client 端**：会话头部按钮 + 浮层面板，粘贴岗位描述 → 生成
- **Host 端**：注册 `intro.generate` 方法，规则引擎分析关键词 + 大模型润色

**两个版本**：

| 版本 | 方案 | 说明 |
|---|---|---|
| `intr-1/pkg-1` | 纯规则引擎 | 关键词匹配（To B/To C、行业、技术方向）→ 拼接真实经历，稳定但机械 |
| `intr-1/pkg-2` | **规则选材 + 大模型润色（混合）** | 规则引擎负责"选什么"（选真实经历片段），大模型负责"怎么写"（润色成自然表达）；模型失败自动回退规则版 |

**致命局限**：Cordis 插件运行在 Harness 网页内，**无法访问 BOSS直聘 页面**（跨域）。用户必须手动复制粘贴 JD。

### 2.2 方案 B：Chrome 扩展（最终采用）

**关键洞察**：BOSS 的"禁止复制"限制的是**用户选择/剪贴板**，但岗位文字必须渲染在 DOM 里用户才能看到。
扩展的 content script **直接读取 DOM 文本**（不走剪贴板），从而绕过复制限制。

**合规性说明**：这是"读取你自己浏览器里已显示的页面内容"，属于个人求职辅助工具，非抓接口、非批量爬取。

### 2.3 最终架构

```
┌─────────────────────────────────────────────┐
│  Chrome 扩展 (Manifest V3)                  │
│                                             │
│  content.js ──── 读取岗位 DOM               │
│      │           猫猫动画 + 面板 UI          │
│      │                                      │
│      ▼  chrome.runtime.sendMessage          │
│  background.js ── 调用 AI API + 存设置       │
│                                             │
│  popup.html ──── 工具栏弹窗（状态/入口）      │
│  options.html ── 设置页（Key/模型/素材）      │
└─────────────────────────────────────────────┘
```

## 三、功能设计

### 3.1 岗位信息抓取（content.js）

三级兜底策略，应对 BOSS 页面改版：

1. **精确选择器**：`.job-title`、`[class*="job-detail"]` 等 13 个候选
2. **标题定位**：查找包含「职位描述/岗位职责/任职要求」的标题节点，向上找容器
3. **全文兜底**：取页面最长文本块（40~6000 字）

其他处理：
- 去除薪资噪声（`30-45K·13薪` 前缀）
- 行去重
- SPA 路由监听（`location.href` 变化 → 自动重新抓取）

### 3.2 自我介绍生成（background.js）

采用与 DSH 插件一致的**混合思路**，但直接在扩展内调用 OpenAI 兼容 API：

```
系统提示词约束（防幻觉核心）：
  1. 只能使用素材中出现的事实，绝不编造经历、数据、公司或项目
  2. 突出与岗位最相关的经历，最有价值的放前面
  3. 语言自然口语化，不要模板腔
  4. 保留姓名和结尾语
  5. 直接输出正文
```

**设置项**（`chrome.storage.sync`）：

| 项 | 默认值 |
|---|---|
| `apiKey` | 空（必填） |
| `baseUrl` | `https://api.deepseek.com/v1` |
| `model` | `deepseek-chat` |
| `name` | 你的姓名（开源版默认留空） |
| `closing` | 有作品集可发，期待您的回复～ |
| `profile` | 4 条真实经历（可编辑，模型只能用它） |

**多服务商支持**：DeepSeek / Kimi / 通义千问 一键预设（均为 OpenAI 兼容）。

**权限处理**：自定义 API 域名通过 `optional_host_permissions` + `chrome.permissions.request()` 动态申请。

## 四、猫猫动画设定

### 4.1 主题定位

**「小猫修理工」**——用户的真实宠物猫，穿着工装、手持电钻，把粗糙的岗位 JD「钻」成精致的自我介绍。

隐喻：**电钻打磨 = 文案优化**。

### 4.2 动作设计（4 个动效）

| 动作 | 素材来源 | 帧数 | 播放速度 | 触发场景 |
|---|---|---|---|---|
| **待机/热身** | `idle_alpha.mov` | **73 帧** | 20fps (50ms) | 浮动按钮默认常驻 |
| **钻钻钻** | `drill_alpha.mov` | 12 帧 | 12fps (85ms) | 生成中「打磨中」 |
| **举手完工** | `hand_alpha.mov` | 12 帧 | 12fps (85ms) | 生成成功 |
| **交付/点赞** | `delivery_alpha.mov` | 12 帧 | 12fps (85ms) | 复制成功 |

> **为什么 idle 用 73 帧、其他只用 12 帧？**
> 这是"选项 C"折中方案：idle 是用户看得最多、时间最长的默认状态，需要完整连贯的动作；
> 其他三个只在面板内短暂出现，12 帧足以表达。这样在**动效质量**与**扩展体积**之间取平衡（若 4 段都用 73 帧，体积将达 80MB+）。

### 4.3 交互状态机

```
[页面打开] ──→ 🐱 待机/热身（浮动按钮常驻，ping-pong 循环）
                    │ 点击猫猫
                    ▼
            [面板打开 + 自动抓取岗位]
                    │ 点「🔧 一键生成自我介绍」
                    ▼
            🔧 钻钻钻（面板头部动画）
                    │ 生成成功
                    ▼
            🎉 举手完工
                    │ 点「📦 完工！拿去用吧」且复制成功
                    ▼
            📦 交付/点赞（2.4s 后回到完工态）
```

### 4.4 UI 文案体系（修理工主题）

| 位置 | 文案 |
|---|---|
| 浮动按钮气泡（轮播） | 喵~ 需要打磨自我介绍吗？ / 🔧 电钻已就位，随时开工～ / 把 JD 给我，帮你钻出好offer！ / 你好呀，小猫修理工在这~ |

## 五、素材制作攻坚（最曲折的部分）

### 5.1 素材来源

用户用 AI 视频工具（豆包）基于**自己的宠物猫照片**生成 4 段动作视频，再由用户完成抠图。

### 5.2 逐层排查：为什么透明通道一直丢失？

这是整个项目最耗时、最曲折的技术排查，前后验证了 **6 种方案**：

| # | 方案 | 结果 | 原因 |
|---|---|---|---|
| 1 | 剪映导出 MOV | ❌ `hevc / yuv420p` | 剪映导出未勾选 alpha，背景变纯黑 |
| 2 | 剪映导出 GIF | ❌ 41 帧均是 `trans_flag=0` | GIF 未设透明索引，仍是黑底 |
| 3 | ffmpeg VP8 alpha | ❌ 输出 `yuv420p` | 本机构建的 libvpx 不支持 alpha |
| 4 | ffmpeg VP9 `yuva420p` | ❌ 输出 `yuv420p` | profile 2 需 10bit，且构建限制 |
| 5 | ffmpeg AV1 / H264 / HEVC / VideoToolbox | ❌ 全部无 alpha | 本机 ffmpeg 编译器层面不支持视频 alpha |
| 6 | **ProRes 4444** | ✅ `yuva444p12le`（真 alpha） | 唯一有 alpha 的编码，但**浏览器不播 ProRes** |
| 7 | APNG | ✅ 有真 alpha | 但体积爆炸（4 段 10-20MB） |

**关键结论**：本机 ffmpeg **无法产出浏览器可播的带 alpha 视频**；而 APNG 体积不可接受。

### 5.3 最终方案：透明 PNG 帧序列 + 前端播放器

**用户提供 ProRes 4444（真 alpha）源文件后**，采用：

```bash
# 从 ProRes 4444 抽帧为带 alpha 的 PNG
ffmpeg -i idle_alpha.mov -vf "scale=320:-2,fps=20" -start_number 0 assets/frames/idle/f_%03d.png
```

**为什么可行**：
- PNG 天然支持 alpha（`rgba64be`），抽帧后透明度**完美保留**（实测 77% 透明 / 23% 猫）
- 前端用 JS 定时切换帧，效果等同视频
- 体积可控（idle 73 帧 ≈ 20MB，其他各 12 帧 ≈ 2-3MB）

**验证结果**：抽出的帧 87% 透明、9% 不透明，边缘干净，猫猫完全漂浮无背景。

### 5.4 素材存放

```
assets/
├── frames/                 # 最终使用的透明帧（打包进扩展）
│   ├── idle/      73 帧
│   ├── drill/     12 帧
│   ├── hand/      12 帧
│   └── delivery/  12 帧
├── 待机和热身.MOV            # 早期黑底源（已废弃）
├── 钻钻钻.MOV
├── 举手完工.MOV
└── 交付.MOV
```

> 353MB 的 ProRes 4444 源文件已移至 `../boss-intro-extension-backup/alpha-src/`，
> **不打包进扩展**，仅作素材备份。

## 六、动画播放器的四次演进

这是体验打磨的核心，共迭代 4 个版本解决 2 类「闪」的问题。

### 6.1 版本 1：`<img>` 换 src + 单向循环

```js
setInterval(() => {
  idx = (idx + 1) % FRAME_COUNT[motion];
  img.src = frameUrl(motion, idx);
}, FRAME_MS);
```

**问题**：播放到末帧后**直接跳回首帧**。而 idle 首帧是"横握电钻"、末帧是"电钻举到头顶"，
两帧姿态差异极大 → **循环接缝处闪一下**。

### 6.2 版本 2：末帧停留

在末帧停留 6 帧时长再回到首帧。

**问题**：停留只是让突变"慢一点"展现，**并未消除硬切** → 仍然闪。

> 经抽帧分析发现：idle 视频的动作流是「横握 → 举高并保持」的**单向渐变**，
> 首末帧本就不构成自然循环，任何"跳回"都是突变。

### 6.3 版本 3：ping-pong 往返播放

```js
idx += dir;
if (idx >= lastIdx) { idx = lastIdx; dir = -1; }   // 到末帧转向
else if (idx <= 0)   { idx = 0;      dir = 1;  }   // 到首帧转向
```

每次转向都是**相邻帧过渡**，理论上彻底消除接缝突变。

**问题**：用户反馈「还是会闪两下」——经查是**图片解码延迟**导致：
232KB 的 PNG 在 50ms/帧的节奏下，`<img src>` 切换可能来不及解码。

### 6.4 版本 4（最终）：帧预加载 + canvas 播放

**双重改进**：

**① 预加载缓存**——创建时把所有帧用 `new Image()` 预加载：
```js
function preloadMotion(motion) {
  const arr = [];
  for (let i = 0; i < FRAME_COUNT[motion]; i++) {
    const im = new Image();
    im.src = frameUrl(motion, i);
    arr.push(im);
  }
  return arr;
}
```

**② canvas 连续绘制**——用户反馈「**猫后面的背景闪过**」，这是 `<img src>` 切换时
「旧帧 → 空档(透明) → 新帧」的中间空档**透出页面**造成的。

改用 `<canvas>` + `requestAnimationFrame`，用 `drawImage` 绘制：
```js
const draw = (i) => {
  ctx.clearRect(0, 0, nw, nh);
  const im = frames[i];
  ... 等比居中绘制 ...
  ctx.drawImage(im, dx, dy, dw, dh);
};
```

**为什么能根治**：`drawImage` 要么画当前帧、要么画前一帧，
**不存在中间空档**，透明区域永远不会透出底下的页面。

**保留能力**：ping-pong 往返、动作切换（`__setMotion`）、时间累积推进（`acc` 支持变速）。

## 七、交互功能

### 7.1 猫猫拖动

用户要求：浮动按钮的猫猫可拖到桌面任意位置。

**实现要点**（content.js）：

```js
// 1. 用 pointer 事件统一鼠标/触屏
fab.addEventListener('pointerdown', ...);
fab.addEventListener('pointermove', ...);
fab.addEventListener('pointerup', ...);

// 2. 位移阈值区分「点击」与「拖动」
if (Math.abs(dx) > 5 || Math.abs(dy) > 5) moved = true;

// 3. 拖动结束保存位置，抑制误触发的 click
onPointerUp: saveFabPos(rect.left, rect.top); fab.__draggedOnce = true;

// 4. 位置持久化
chrome.storage.local.set({ bossIntroFabPos: { left, top } });
```

**细节处理**：
- 初始用 `right/bottom` 定位，拖动开始时换算成 `left/top`
- 边界钳制：不超出视口（`Math.max(0, Math.min(pos, vw - 60))`）
- `img.draggable = false` 避免原生图片拖拽冲突
- 下次打开页面自动恢复位置

### 7.2 其他交互

- **气泡轮播**：4 句文案每 4 秒切换
- **hover/active 缩放**：`scale(1.08)` / `scale(0.96)`
- **SPA 路由感知**：切换岗位自动重新抓取
- **面板关闭**：猫猫回到 idle

## 八、文件清单与安装

### 8.1 目录结构

```
boss-intro-extension/

└── assets/
    ├── frames/            # 透明帧动画（四组）
    └── *.MOV              # 早期黑底源素材
```

### 8.2 manifest 关键点

```json
{
  "manifest_version": 3,
  "permissions": ["storage"],
  "host_permissions": ["https://api.deepseek.com/*"],
  "optional_host_permissions": ["https://*/*"],
  "content_scripts": [{ "matches": ["https://*.zhipin.com/*"], "js": ["content.js"] }],
  "web_accessible_resources": [
    { "resources": ["assets/frames/*"], "matches": ["https://*.zhipin.com/*"] }
  ]
}
```

**关键**：`web_accessible_resources` 声明 `assets/frames/*`，
否则 content script 无法通过 `chrome.runtime.getURL()` 加载帧图片。

### 8.3 安装步骤

1. `chrome://extensions/` → 开启「开发者模式」
2. 「加载已解压的扩展程序」→ 选择 `boss-intro-extension` 文件夹
3. 点扩展图标 → 打开设置 → 填 API Key → 保存 → 测试连接
4. 打开 BOSS 岗位页 → 点右下角猫猫

### 8.4 更新方式

修改代码后，在 `chrome://extensions/` 点「**重新加载**」，刷新页面即可，无需重装。

## 十、关键经验总结

1. **跨站限制决定架构**：Cordis 插件无法访问第三方站点 DOM，Chrome 扩展才是正解。
2. **"禁止复制" ≠ "无法读取"**：DOM 文本始终可读，扩展是读取已渲染内容，合规且有效。
3. **alpha 通道是坑**：工具链（剪映/ffmpeg 构建）的 alpha 支持差异极大，务必**先验证输出格式**（`ffprobe` 看 `pix_fmt` 是否 `yuva*`）再批量处理。
4. **帧动画的"闪"有两类**：①帧序接缝突变（解法：ping-pong）②img 换 src 的解码空档透底（解法：canvas drawImage）。
5. **预加载是帧动画的基本功**：不预加载必然在低帧间隔下闪帧。
6. **先确认素材质量再动手**：素材（alpha、帧率、动作连贯性）决定上限，后期补救成本极高。
